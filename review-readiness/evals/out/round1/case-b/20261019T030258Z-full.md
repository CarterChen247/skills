## 5. Confirmed findings
- **D1** · `src/webhooks/refundHandler.ts:26` (insert) vs `:18` (lookup)
  - Scenario: Stripe delivers `evt_1` (refund `re_1`, 500). Line 26 records `eventId: "re_1"` and the balance is credited. Stripe retries `evt_1`. Line 18 looks for `eventId: "evt_1"`, finds nothing, and `applyRefund` (documented "Not idempotent", `src/billing/refunds.ts:3`) credits another 500. Result: a double refund, i.e. INC-2291 again.
  - Why CI is green: test 2 (`tests/webhooks/refundHandler.test.ts:13-17`) inserts `evt_1` by hand instead of processing the event first.
  - Fix: insert `eventId: event.id` at line 26. Add a regression test that calls `handleRefundEvent(evt)` twice and asserts `"duplicate"` plus a balance of 500.

## 6. Unverified risks (hypotheses)
- **D2** · Two concurrent deliveries of the same event can both pass the lookup at `refundHandler.ts:18` before either commits. Nothing at the DB level stops this: the lookup is outside the `db.transaction` at :24, and `0043_processed_events.sql:5` creates a non-unique index with no PK. Both would call `applyRefund`.
  - Plausible because Stripe retries on timeout while the first attempt may still be running.
  - Confirm or refute: check how the webhook route and workers run concurrently, or test two parallel calls. Fix: a UNIQUE/PK on `event_id`, with the insert done first inside the txn (or `INSERT … ON CONFLICT DO NOTHING` and checking the affected rows).
