## 6. Unverified risks (hypotheses)
- **D1** · `src/http/authMiddleware.ts:8-13` (`requireAuth`). A request with no token and the header `X-Internal-Service: <listed name>` gets `principal = {kind:"service"}` and skips JWT verification. The header value looks like a plain service name, not a secret. This applies to every route behind `requireAuth`, not only `/internal`. **Confirm/refute:** read the `INTERNAL_SERVICES` definition, check whether ingress strips or authenticates this header (mTLS, network policy), and check where `requireAuth` is mounted.
- **D2** · `src/ledger/transfer.ts:~11` (`await notifyTransfer(...)` inside `withSerializableRetry`, `maxAttempts: 5`). If a serialization failure happens at or after the notify (e.g. at COMMIT), the callback re-runs and the partner gets a duplicate webhook. If all attempts fail, the partner gets a webhook for a transfer that never committed. **Confirm/refute:** read `src/db/txn.ts:withSerializableRetry` to see what it retries and where it commits. The fix is to emit after commit (outbox pattern) with an idempotency key.
- **D3** · `src/ledger/transfer.ts:~5-9`. Only `src` is checked among the locked rows, so a non-existent `to` depends on how `tx.accounts.credit` behaves (silent no-op means lost money). `from === to` is also unhandled. The new `idemKey` parameter is accepted but never used. **Confirm/refute:** read `tx.accounts.credit` and the tests.
- **Downstream authz** · Handlers may assume `req.principal` is a user (from JWT). A `kind: "service"` principal could break or widen authz checks. **Confirm/refute:** grep the `req.principal` consumers.
