## 5. Confirmed findings
- **D1** · `src/webhooks/refundHandler.ts:26` (vs lookup at `:18`) · Stripe delivers `evt_1` (refund `re_1`); first call inserts `{eventId: "re_1"}`. Stripe redelivers `evt_1` (author-documented at-least-once) → `findOne({eventId: "evt_1"})` returns null → `applyRefund` (`src/billing/refunds.ts:3`, "Not idempotent") credits the balance a second time. · Fix: insert `eventId: event.id`; add a regression test that calls `handleRefundEvent(evt)` twice and asserts balance 500 and second result `"duplicate"`.

## 6. Unverified risks (hypotheses)
- **D2** · Two concurrent deliveries of the same event both pass `findOne` at `refundHandler.ts:18` before either commits; migration has only a non-unique index (`0043_processed_events.sql:5`), so both inserts succeed → double refund. · Confirm/refute: does Stripe (or our ingress/workers) process the same event in parallel? Safer regardless: `UNIQUE(event_id)` + insert-first inside the txn, treating the unique violation as `duplicate`.
